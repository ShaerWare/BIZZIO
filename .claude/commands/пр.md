# Скилл «пр» — полный цикл: PR → Merge в develop → Зеркало в BizzioDev → Deploy на ТЕСТ → Канбан

Выполни полный цикл выпуска изменений на **тестовый** контур Bizzio.ru. Работай автономно,
спрашивай только если что-то критически неясно.

> **По умолчанию заливаем на ТЕСТ, а не на прод.** Прод (bizzio.ru) — отдельный явный шаг
> (см. раздел «Промоушен на прод»), выполняется только по прямой просьбе пользователя.

## Контекст — ДВЕ репы

| | Основная (разработка) | Зеркало (заказчик) |
|---|---|---|
| Репо | `ShaerWare/BIZZIO` | `BizzioDev/BIZZIO` |
| Видимость | public | **private** (организация на free-плане) |
| Remote локально | `origin` | `customer` |
| Что там живёт | PR, issues, канбан, ревью | только код (`develop`, `main`) |

**Правило зеркалирования: код должен лежать в обеих репах одинаково.** Разработка ведётся
в ShaerWare (там issues и канбан), а после каждого мерджа в `develop`/`main` та же ветка
пушится в `customer` — заказчик всегда видит актуальный код. PR-ы и feature-ветки в зеркало
НЕ пушим, только `develop` и `main`.

- Пайплайн: **feature-ветка → PR в `develop` (ShaerWare) → проверки CI → merge → зеркальный
  пуш в `customer` → авто-деплой на test.bizzio.ru**.
  Прод: `develop → PR в main (ShaerWare) → ручное подтверждение (Environment `production`) →
  bizzio.ru → зеркальный пуш main в `customer``.
- `develop` и `main` в ShaerWare защищены: обязательные проверки **Tests**, **Code style (Pint)**,
  **Assets freshness**. Поэтому в `develop` пушим только через PR (не напрямую).
  В BizzioDev защиты веток НЕТ — иначе зеркальный пуш был бы отклонён.
- **Деплой.** `.github/workflows/ci.yml` идентичен в обеих репах, у обеих есть секреты
  `SSH_HOST` / `SSH_USER` / `SSH_PRIVATE_KEY`, поэтому деплой запускается из обеих:
  - **Тест:** пуш в `develop` в ShaerWare → job `Deploy develop -> test.bizzio.ru`. В зеркале
    пуш-триггер не срабатывает, поэтому ран там запускается явно (`gh workflow run`, см. шаг 8).
    Оба запуска раскатывают один и тот же коммит и сериализованы через `flock`
    (`/var/lock/bizzio-test-deploy.lock`) — параллельного деплоя не будет.
  - **Прод:** авто-деплой по пушу в `main` работает **только в ShaerWare** (там Environment
    `production` реально гейтит запуск ручным подтверждением). В BizzioDev прод раскатывается
    только вручную: Actions → CI/CD → Run workflow → `target: prod` (approval-гейт там
    недоступен — free-план + приватная репа).
  - **Сервер тянет код из ShaerWare** (`origin` = `https://github.com/ShaerWare/BIZZIO.git`,
    анонимный HTTPS): приватную репу он читать не может, потому что deploy keys запрещены
    политикой организации BizzioDev. Поэтому **зеркальный пуш обязателен, но источником для
    сервера остаётся ShaerWare** — расхождение реп означает, что заказчик видит не тот код,
    который раскатан.
- Руками по SSH на сервер ходить НЕ нужно.
- Тест под basic-auth: `curl -sI https://test.bizzio.ru` отдаёт `HTTP/1.1 401` — это норма (сайт живой).
- Локально: Node доступен (`npm run build`), тесты и Pint гоняем в Docker-контейнере `my_project_app`.
- Changelog: `docs/CHANGELOG_CLAUDE.md`. Канбан: https://github.com/users/ShaerWare/projects/4

Проверь, что remote `customer` заведён (одноразово, если его нет):

```bash
git remote -v | grep -q '^customer' || git remote add customer https://github.com/BizzioDev/BIZZIO.git
```

## Шаги

### 1. Разведка

```bash
git status --short
git branch --show-current
git log --oneline -5
git diff --stat
gh issue list --state open --limit 20 --repo ShaerWare/BIZZIO
```

Определи: какие файлы изменены, на какой ветке, какие open issues связаны с изменениями.

### 2. Обнови CHANGELOG (ОБЯЗАТЕЛЬНО, до коммита)

Запиши краткий отчёт в конец `docs/CHANGELOG_CLAUDE.md`: дата, что сделано, какие файлы
изменены, причина ошибки (если багфикс). Должно уйти тем же PR.

### 3. Обнови CLAUDE.md (если нужно)

Обнови, если добавлены новые роуты/контроллеры/модели/сервисы/джобы, изменена схема БД
или архитектурные конвенции. **Пропусти** для мелких багфиксов и стилевых правок.

### 4. Прогони проверки локально (как в CI)

```bash
docker compose exec -T app php artisan key:generate --force   # если тесты падают с MissingAppKey
docker compose exec -T app php artisan test
docker compose exec -T app ./vendor/bin/pint --test
```

**Assets freshness (частая причина падения CI).** Если менялись blade/JS/CSS и особенно если
добавлены новые Tailwind-классы — пересобери ассеты и закоммить `public/build`.
`tailwind.config.js` сканирует `storage/framework/views/*.php` (кэш скомпилированных вью),
поэтому чтобы сборка совпала с чистым checkout'ом CI, **сначала очисти кэш вью**:

```bash
rm -f storage/framework/views/*.php   # или: docker compose exec -T app php artisan view:clear
npm run build
git status --short public/build       # если изменилось — добавь в коммит
```

Собери дважды и убедись, что хэш CSS стабилен (детерминизм).

### 5. Коммит на feature-ветке

Не коммить в `develop`/`main` напрямую (защищены). Создай ветку:

```bash
git checkout -b fix/краткое-описание      # или feat/…
git add app/ resources/ routes/ tests/ docs/ public/build   # НЕ .env, НЕ credentials
git commit -m "$(cat <<'EOF'
fix|feat|docs: краткое описание

Детальное описание изменений.

Co-Authored-By: Claude Opus 4.8 (1M context) <noreply@anthropic.com>
EOF
)"
```

> Триколонку `Co-Authored-By` бери из активной модели сессии (см. системный контекст),
> а не хардкодь версию.

### 6. Push + PR в develop (только ShaerWare)

Feature-ветку пушим ТОЛЬКО в `origin` — в зеркало ветки разработки не попадают.

```bash
git push -u origin <ветка>
gh pr create --repo ShaerWare/BIZZIO --base develop --head <ветка> \
  --title "…" --body "…"
```

Тело PR: `## Summary` (буллеты), `## Test plan` (чеклист). По ключевым словам закрытия:
- Если задача **полностью закрывается и уже проверена** — можно `Closes #N`.
- Если правки идут **на ре-тест** (типовой случай для этого пайплайна) — пиши `Relates to #N`,
  чтобы issue НЕ закрылась автоматически до проверки тестировщиком.

Дождись зелёных проверок и замерджи:

```bash
gh pr checks <PR> --repo ShaerWare/BIZZIO      # ждём pass: Tests, Pint, Assets freshness
gh pr merge <PR> --repo ShaerWare/BIZZIO --merge
```

Вернись на develop и подчисти ветку:

```bash
git checkout develop && git pull origin develop
git branch -D <ветка>
git push origin --delete <ветка>
```

### 7. Проверь авто-деплой на тест (ShaerWare)

Merge в `develop` запускает push-run воркфлоу с job'ом деплоя на тест:

```bash
RUN=$(gh run list --repo ShaerWare/BIZZIO --branch develop --limit 1 --json databaseId -q '.[0].databaseId')
gh run view $RUN --repo ShaerWare/BIZZIO --json status,conclusion,jobs \
  -q '(.status+"/"+(.conclusion//"running")), (.jobs[]? | "  \(.name): \(.status)/\(.conclusion//"-")")'
```

Убедись, что `Deploy develop -> test.bizzio.ru` = `completed/success`.

> **Transient-сбой GitHub Actions.** Иногда push-run падает сразу с сообщением
> «This run likely failed because of a workflow file issue» и **пустым списком джобов**
> (сам workflow-файл при этом не менялся). Это инфраструктурный глюк — просто перезапусти:
> `gh run rerun <RUN> --repo ShaerWare/BIZZIO`, затем снова проверь статус.

Проверь, что тест отвечает (401 = норма, basic-auth):

```bash
curl -sI https://test.bizzio.ru | head -3
```

### 8. Зеркальный пуш в BizzioDev

**Только после успешного деплоя из ShaerWare** — чтобы два деплой-рана не толкались на сервере
(flock их сериализует, но ждать блокировку 20 минут незачем).

```bash
git push customer develop
git ls-remote origin develop && git ls-remote customer develop   # SHA должны совпасть
```

> **Пуш в зеркало НЕ создаёт workflow run** (проверено: после реального пуша
> `gh api repos/BizzioDev/BIZZIO/actions/runs` показывает `total_count` без него, хотя
> воркфлоу `active` и ручной запуск работает). Поэтому ран в зеркале запускаем явно.

Запусти деплой в репе заказчика и дождись его (повторная раскатка того же коммита —
идемпотентна и защищена flock'ом):

```bash
gh run list --repo BizzioDev/BIZZIO --limit 1 --json headSha,event   # вдруг push-run всё же появился
gh workflow run "CI/CD" --repo BizzioDev/BIZZIO --ref develop -f target=test
sleep 10
RUN=$(gh run list --repo BizzioDev/BIZZIO --limit 1 --json databaseId -q '.[0].databaseId')
gh run watch $RUN --repo BizzioDev/BIZZIO --interval 20 > /dev/null
gh run view $RUN --repo BizzioDev/BIZZIO --json status,conclusion,jobs \
  -q '(.status+"/"+(.conclusion//"running")), (.jobs[]? | "  \(.name): \(.status)/\(.conclusion//"-")")'
```

Если push-run всё-таки появился (GitHub починил триггер) — ручной запуск не нужен, просто
дождись пуш-рана; двойной деплой безопасен, но бессмыслен.

Если пуш отклонён (`non-fast-forward`) — значит в зеркале появились посторонние коммиты.
НЕ форсируй молча: покажи расхождение (`git log customer/develop --oneline -5`) и спроси
пользователя.

### 9. Канбан — перенеси задачи в «In review (test)»

**Правило.** После заливки на тест карточки решённых задач переезжают в колонку тестирования
**«In review (test)»**:
- **«сделал»** (реализовал фичу/задачу) → перенеси карточку в «In review (test)».
- **«поправил»** (внёс правки по замечаниям) → перенеси карточку из «Правки после тестов» в «In review (test)».

Проект: `PVT_kwHOBdqTXs4BNXwK`, поле Status: `PVTSSF_lAHOBdqTXs4BNXwKzg8YsU0`,
опция «In review (test)»: `df73e18b` (опция «Правки после тестов»: `9b8cc430`).
Если ID изменились — перечитай их: `gh project field-list 4 --owner ShaerWare --format json`.

Найди item-id нужных issue и перемести:

```bash
# item-id по номеру issue:
gh project item-list 4 --owner ShaerWare --format json --limit 200 \
  | python -c "import json,sys; [print(i['id'], i.get('content',{}).get('number')) for i in json.load(sys.stdin)['items'] if i.get('content',{}).get('number') in {NNN}]"

# перенос:
gh project item-edit --project-id PVT_kwHOBdqTXs4BNXwK \
  --field-id PVTSSF_lAHOBdqTXs4BNXwKzg8YsU0 --single-select-option-id df73e18b --id <ITEM_ID>
```

Issue при этом **оставляем открытыми** (закроются позже, при промоушене develop→main), если
только задача не подтверждена и не закрывается явно.

### 10. Финальный отчёт

Выведи пользователю: номер и ссылку PR, статус проверок, статус деплоя на тест
(`Deploy develop -> test.bizzio.ru`), подтверждение, что зеркало `BizzioDev/BIZZIO` синхронно
(совпадение SHA develop), какие карточки перенесены в «In review (test)», что изменено (кратко).
Напомни, что промоушен на прод — отдельный шаг по запросу.

## Промоушен на прод (только по явной просьбе)

Выполняй ТОЛЬКО когда пользователь прямо просит «на прод»/«в прод»/«на bizzio.ru».
Прод — это `main`, деплой гейтится ручным подтверждением в GitHub (Environment `production`
в ShaerWare).

```bash
gh pr create --repo ShaerWare/BIZZIO --base main --head develop \
  --title "release: develop → main" --body "Промоушен протестированных изменений на прод."
gh pr checks <PR> --repo ShaerWare/BIZZIO       # дождись зелёных
gh pr merge <PR> --repo ShaerWare/BIZZIO --merge
```

После merge в `main` job `Deploy main -> bizzio.ru` ждёт **ручного подтверждения** в GitHub
Actions (Environment `production`). Подтвердить деплой должен пользователь (у Claude нет доступа
к approval). После аппрува проверь:

```bash
curl -sI https://bizzio.ru | head -5      # ожидаем HTTP/2 200
```

Затем зеркаль `main` заказчику:

```bash
git fetch origin main && git push customer refs/remotes/origin/main:refs/heads/main
git ls-remote origin main && git ls-remote customer main   # SHA должны совпасть
```

Пуш `main` в зеркало прод-деплой не запускает (авто-деплой прода ограничен репой ShaerWare,
да и пуш-триггер в зеркале не срабатывает) — это правильно: прод раскатывается ровно один раз
и только после аппрува.

Ручной прод-деплой из репы заказчика (если понадобится — approval-гейта там нет, деплой
пойдёт сразу): Actions → CI/CD → Run workflow → ветка `main`, `target: prod`. Или:

```bash
gh workflow run "CI/CD" --repo BizzioDev/BIZZIO --ref main -f target=prod
```

Ручной фолбэк-деплой на прод по SSH (если CI-деплой недоступен; ассеты уже в git, npm на
сервере НЕТ):

```bash
ssh -i ~/.ssh/bizzio_deploy root@159.194.219.159 "cd /var/www/BIZZIO && \
  git fetch origin main && git reset --hard origin/main && bash scripts/deploy.sh"
```

## Что настроено в BizzioDev/BIZZIO (справочно)

- Приватная репа, default branch `develop`, защиты веток нет (нужна для зеркального пуша).
- Секреты `SSH_HOST` / `SSH_USER` / `SSH_PRIVATE_KEY` — те же, что в ShaerWare.
- Environment `production` создан, но **без required reviewers**: правило недоступно на
  free-плане для приватной репы. Поэтому авто-деплой прода там выключен условием
  `github.repository == 'ShaerWare/BIZZIO'` в `ci.yml`.
- Deploy keys в организации запрещены политикой — сервер не может тянуть приватную репу,
  поэтому `origin` на сервере остаётся `ShaerWare/BIZZIO`.
- Чтобы перевести сервер на репу заказчика, владелец организации (MSverlov) должен разрешить
  deploy keys; тогда на сервере уже лежит готовый ключ `~/.ssh/bizzio_repo`
  (+ запись в `~/.ssh/config`) — останется добавить его публичную часть в Settings → Deploy keys
  и переключить `origin` в `/var/www/bizzio-test` и `/var/www/BIZZIO` на
  `git@github.com:BizzioDev/BIZZIO.git`.
